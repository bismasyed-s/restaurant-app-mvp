Assignment no. 2
Restaurant App with Server and Database (React Native, Node.js, MongoDB), Fall 2026
In A1, your Restaurant App ran completely on mock data saved inside the app. It worked, but it had a big limitation. If the manager changes the price of a dish on his phone, customers still see the old price on their phones. If someone reinstalls the app, all their orders and bookings are gone. Every phone has its own copy of the data and none of them talk to each other.
Real apps solve this with a server and a database. All phones send their data to the server, the server saves it in the database, and every phone reads from the same place. In this assignment you will add these two pieces to the app you already made.
- Customer: "I placed an order from my phone, but when I checked on my brother's phone it wasn't there."
- Restaurant Manager: "When a dish runs out, I want to mark it unavailable once and have every customer see it."
Task: Before you write any code, open your A1 app and use it for a few minutes. Note down where the app loses data or shows different data on different phones. You will use this list in the SRS update (Question 1), and by the end of the assignment each problem on it should be fixed.
You are not starting over. Your A1 screens, context, reducers, and hooks will stay. Mostly you will be building a small server and then changing where your screens get their data from.

## Deliverables
- Updated SRS: Your A1 SRS revised to include the server, the database, and the list of API endpoints.
- Backend: A Node.js and Express server connected to MongoDB, with APIs for users, menu, reservations, and orders.
- Connected App: The A1 app using the server instead of mock files.

## Before You Start
Install and set up the following before the first lab of this assignment. Please do not leave it for the last week.
- Node.js (LTS) and npm. You should already have these from A1.
- MongoDB. You can create a free cluster on MongoDB Atlas, or install MongoDB Community Server with Compass on your laptop. Atlas is easier if you work from different networks.
- Postman, or the Thunder Client extension in VS Code, to test the API.
- Your A1 project running on Expo Go or an emulator.
Note: when the app runs on your phone, "localhost" refers to the phone, not your laptop. So in the app you have to use your laptop's IP address, for example http://192.168.1.15:5000, and both devices must be on the same Wi-Fi. If you are using the Android emulator, use http://10.0.2.2:5000. If you get "Network request failed", check this first.

## Question 2: Express Server Setup
Concepts covered: Node.js, Express, environment variables
Objective: Get a basic server running and make sure your phone can reach it. Do this before adding the database.

## Requirements
- Make a folder named server in the root of your repository, outside the React Native src folder. Run npm init and install express, cors, and dotenv. Install nodemon as a dev dependency.
- Inside server, create the folders config, models, routes, controllers, and middleware. Your main file will be server.js.
- Create a .env file with PORT=5000 and MONGO_URI (you can leave it empty for now) and load it using dotenv. Put .env in .gitignore. Also add a .env.example file with the same keys and no real values, and commit that one.
- Make a GET /api/health route that returns { "status": "ok", "time": <current time> }.
- Add a "start" script (node server.js) and a "dev" script (nodemon server.js) to package.json.
- For any URL that does not exist, return 404 with the message "Route not found". Add an error handler at the end of server.js that sends back a JSON error with status 500.
- Check the health route in Postman. Then open it in your phone's browser using your laptop's IP. If the phone can't open it, check the Wi-Fi and your firewall settings for port 5000.
Deliverable: The server folder, .env.example, and two screenshots: one from Postman and one from your phone's browser.

## Question 3: Connecting to MongoDB
Concepts covered: Mongoose, schemas, models, seeding
Objective: Connect your server to the database and move your A1 mock data into it.

## Requirements
- Create a database named restaurant_app on Atlas or on your laptop and put the connection string in MONGO_URI. On Atlas, you also need to add your IP address under Network Access.
- Write config/db.js to connect with mongoose.connect. Print "MongoDB connected" when it works. If it fails, print the error and stop the server with process.exit(1).
- Make Mongoose models for User, MenuItem, Table, Reservation, and Order based on your database design. Use required, unique, enum, min, and default where needed. For example, price should not be negative, and order status can only be Pending, Preparing, Ready, Served, or Cancelled.
- Turn on timestamps for Order and Reservation so that createdAt and updatedAt are saved automatically.
- Write a seed.js file that empties the collections and inserts your A1 data. You need at least one customer, one manager, fifteen menu items, and six tables. Add "seed" to your npm scripts so you can run it with npm run seed.
- Run it, and check in Compass or Atlas that the data is actually there.
Deliverable: config/db.js, the models folder, seed.js, and a screenshot of the menuitems collection.

## Question 4: Menu API
Concepts covered: REST routes, controllers, CRUD, HTTP status codes
Objective: Build all the menu endpoints and test them in Postman before you connect the app.

## Requirements
- Create routes/menuRoutes.js and controllers/menuController.js. The routes file should only map URLs. All database code goes in the controller.
- GET /api/menu should return all items. It should also work with two optional query parameters, category (for example /api/menu?category=Mains) and search, which matches the item name and is not case sensitive.
- GET /api/menu/:id returns one item. If there is no item with that id, return 404 with a proper message.
- POST /api/menu adds an item and returns 201. PUT /api/menu/:id updates an item and DELETE /api/menu/:id deletes one.
- Use the correct status codes: 200, 201, 400 for missing or wrong data, 404 for not found, and 500 for server errors. Use try and catch in every controller function.
- If someone sends an invalid MongoDB id in the URL, the server should return 400 and not crash.
- Test each endpoint in Postman. Include at least three requests that should fail, such as a missing name, a negative price, or a wrong id. Save everything in one Postman collection.
Deliverable: The routes and controller files, the exported Postman collection (restaurant-api.postman_collection.json), and screenshots of one request that works and one that fails.

## Question 5: Signup, Login, and Protected Routes
Concepts covered: password hashing, JWT, middleware
Objective: Save passwords safely and control who is allowed to call which endpoint.

## Requirements
- Install bcryptjs and jsonwebtoken, and add JWT_SECRET to both .env and .env.example.
- POST /api/auth/register should hash the password with bcrypt before saving the user. If the email is already registered, return 409. Change your seed script so the seeded users also have hashed passwords.
- POST /api/auth/login checks the email and password and returns a token that expires in one day, along with the user's name, email, and role. Do not send the password back in any response, not even the hashed one.
- In middleware/auth.js, write two functions. protect reads the token from the Authorization header (Bearer <token>), verifies it, and puts the user in req.user. managerOnly lets the request through only if the role is manager, otherwise it returns 403.
- Anyone can view the menu, but adding, editing, or deleting an item should need both protect and managerOnly.
- Test it in Postman and take screenshots of three cases: adding an item with no token (401), with a customer token (403), and with a manager token (201).
Deliverable: authRoutes.js, authController.js, middleware/auth.js, and the three screenshots.

## Question 6: Connecting the App to the Server
Concepts covered: fetch or axios, async and await, loading and error states, AsyncStorage
Objective: Make your A1 screens load data from the server instead of the mock files. You will see that the screens themselves do not change much.

## Requirements
- Create src/api/client.js. Put BASE_URL (your laptop's IP and port) here, in one place only. Write a helper function that sends requests, adds the JSON header and the token if there is one, and throws an error with the server's message if the request fails. You can use fetch or axios.
- Connect the Login and Signup screen to /api/auth/register and /api/auth/login. Save the token and user in AuthContext and also in AsyncStorage, so the user stays logged in after closing the app. Logout should clear both.
- On the Menu screen, the useEffect that used a fake Promise in A1 should now call GET /api/menu. The loading indicator, error message, Retry button, and pull to refresh should all still work.
- Make a custom hook, src/hooks/useApi.js, that returns data, loading, error, and refetch. Use it in at least two screens.
- In the Manager Dashboard, adding an item, changing a price, and turning availability on or off should now call the protected endpoints. Reload the list from the server after each change.
- Remove the mock menu and users files, and the AsyncStorage code that was saving menu changes. The server keeps this data now.
- Test using two devices, two phones or a phone and an emulator. Log in as manager on one and change a price, then pull to refresh on the other one. The new price should appear.
Deliverable: src/api/client.js, useApi.js, the updated screens, and screenshots from both devices showing the same new price.

## Question 7: Orders and Reservations
Concepts covered: server side validation, business rules, polling
Objective: Move orders and reservations to the server, and let the server decide what is allowed and what is not.

## Requirements
- Make the following order endpoints: POST /api/orders to place an order, GET /api/orders/my for the customer's own orders, GET /api/orders for the manager to see all orders, and PATCH /api/orders/:id/status for the manager to change the status.
- When an order is placed, the server should work out the total using the prices in the database, and should not accept items that are unavailable. Don't use the total sent by the app. Add a short comment in the code on why.
- Status can only go forward: Pending, Preparing, Ready, Served. An order can be Cancelled only while it is Pending. Any other change should return 400 with a message.
- Make the reservation endpoints: POST /api/reservations, GET /api/reservations/my, GET /api/reservations for the manager, and PATCH /api/reservations/:id so the manager can accept or decline. Before saving a booking, the server must check that the table is free at that date and time and has enough seats. If it is already booked, return 409.
- Connect the app to these endpoints: placing an order, My Reservations, and the Manager Dashboard tabs. Keep your A1 validation in the app too, since it gives the user quick feedback, but the server's check is the one that counts.
- On the Order Tracking screen, remove the fake timer from A1. Instead, use useEffect with setInterval to call GET /api/orders/my every ten seconds, so the customer sees the status change when the manager updates it. Clear the interval in the cleanup function.
- Test the whole flow on two devices. The customer places an order and books a table. The manager accepts the booking and changes the order to Ready. The customer should see both changes without restarting the app.
Deliverable: The order and reservation routes and controllers, the updated screens, and a screen recording (not more than four minutes) of the two device test. Put the link in the README.

## Common Errors
Most students run into one or more of these. Please check this table before asking for help.

| Error | What to check |
|---|---|
| Network request failed | Use your laptop's IP instead of localhost. Both devices must be on the same Wi-Fi, and the server must be running. |
| MongoServerSelectionError | On Atlas, add your current IP in Network Access. Also check the username and password in MONGO_URI. |
| req.body is undefined | Add app.use(express.json()) before your routes. |
| CORS error | Add app.use(cors()) in server.js. |
| 401 on every request | The header should be Authorization: Bearer <token>, with one space after Bearer. |
| Worked yesterday, not today | Your laptop's IP may have changed. Update BASE_URL. |
